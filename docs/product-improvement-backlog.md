# 제품 완성도 개선 백로그

작성일: 2026-09-23

기준 브랜치: `main` (`cf287d5`, PR #23 병합 직후)

이 문서는 현재 앱을 전체 검토한 결과 중 기능은 존재하지만 실제 사용에서 막히거나 어색하게 느껴질 부분을 구현 가능한 작업 단위로 정리한다. 요구사항의 원본은 [inception.md](inception.md), 금융·권한 계약은 [design.md](design.md), 기존 작업 계약은 [implementation-handoff.md](implementation-handoff.md), 알려진 계약 차이는 [code-review.md](code-review.md)를 따른다. 문서가 충돌하면 금융 정합성과 접근 권한에 대해서는 `design.md`와 `implementation-handoff.md`를 우선한다.

## 실행 원칙

1. 한 번에 아래 작업 하나만 구현한다. 여러 항목을 한 PR에 묶지 않는다.
2. 깨끗한 최신 `main`에서 표에 적힌 브랜치를 생성한다. 사용자 작업이 있으면 덮어쓰지 않는다.
3. 작업 전 관련 화면, repository, RPC, 기존 테스트를 읽고 현재 동작을 재현한다.
4. 발견한 문제를 재현하는 테스트를 먼저 추가하거나, UI 작업이면 완료 기준을 검증하는 위젯 테스트를 함께 추가한다.
5. 화면에서 Supabase 쿼리를 직접 만들지 않는다. 데이터 계약은 repository를 통해 사용한다.
6. 금융 쓰기는 기존 RPC를 우회하지 않는다. 직접 테이블 쓰기를 추가하지 않는다.
7. 한국어와 영어 문자열을 동시에 추가한다. 사용자 노출 문구를 Dart 코드에 하드코딩하지 않는다.
8. 관련 테스트, 전체 `flutter test`, `flutter analyze`, `git diff --check`를 실행한다. UI 변경은 최소 macOS debug build도 확인한다.
9. DB 변경은 새 migration으로만 추가하고 기존 migration을 고치지 않는다. 관련 pgTAP 테스트를 추가한다.
10. 결과와 미검증 항목을 `docs/construction.md`에 기록한다. 외부 설정이나 실기기 검증을 실행하지 않았다면 완료로 표현하지 않는다.

## UX01 — 조회 로딩·실패·재시도 상태 통일

권장 브랜치: `fix/query-loading-error-states`

### 현재 문제

- `lib/main.dart`의 월 요약 `FutureBuilder`는 `snapshot.data`만 전달한다. 로딩과 오류가 모두 `null`이어서 오류가 나도 0원 요약처럼 보일 수 있다.
- 캘린더 `FutureBuilder`도 오류를 별도로 처리하지 않아 조회 실패 후 `CircularProgressIndicator`가 계속 보일 수 있다.
- 내역 오류 카드는 메시지만 있고 재시도 동작이 없다.
- 지갑은 재시도가 있지만 다른 탭과 표현이 다르다.

### 구현 범위

- 캘린더, 월 요약, 내역, 지갑의 상태를 `loading`, `data`, `empty`, `error`로 구분한다.
- 오류 상태에는 현지화된 설명과 `다시 시도` 버튼을 둔다.
- 재시도는 같은 선택 월과 필터를 유지한 채 future만 다시 생성한다.
- 기존 데이터가 있는 상태에서 새로고침할 때는 전체 화면을 빈 스피너로 교체하지 않는다. 기존 데이터를 유지하고 작은 진행 표시를 사용하는 방식을 우선한다.
- 공통 위젯은 실제로 3곳 이상에서 같은 표현을 사용할 때만 추출한다.

### 제외 범위

- 오프라인 캐시, 자동 지수 백오프, 전역 상태 관리 패키지 도입.
- Supabase 오류 원문 노출.

### 완료 기준

- 월 조회 실패가 0원 데이터 또는 무한 로딩으로 보이지 않는다.
- 캘린더와 내역에서 재시도하면 동일 월을 다시 조회한다.
- 빈 거래와 조회 실패가 서로 다른 화면으로 표시된다.
- 성공한 재시도 후 오류 화면이 사라지고 데이터가 나타난다.

### 테스트

- repository future가 대기 중일 때 로딩 상태.
- 예외를 반환할 때 오류 문구와 재시도 버튼.
- 첫 호출 실패, 두 번째 호출 성공 시 데이터 표시.
- 빈 결과는 오류가 아니라 빈 상태로 표시.

## TX01 — 거래 상세·수정·삭제 연결

권장 브랜치: `feat/transaction-detail-edit-void`

### 현재 문제

거래 목록은 조회만 가능하다. 잘못 저장한 날짜, 금액, 사용처 등을 앱에서 수정하거나 삭제할 수 없다. DB에는 `edit_transaction`과 `void_transaction` RPC 및 version 충돌 계약이 이미 있다.

### 구현 범위

- 거래 행을 누르면 거래 상세 화면을 연다.
- 상세 화면에 유형, 날짜, 금액, 사용처, 카테고리, 결제/입금 수단, 실제 사용자, 메모를 표시한다.
- 수정은 기존 `EntryForm`에 현재 거래를 초안으로 주입해 수행한다.
- 저장 시 현재 거래 ID, `expected_version`, 첫 전송 전에 만든 `request_id`를 repository에 전달한다.
- 삭제는 물리 삭제가 아니라 `void_transaction`을 호출한다. 영향 안내 확인 다이얼로그를 먼저 표시한다.
- `version_conflict`이면 자동 덮어쓰기하지 않는다. 최신 데이터가 변경되었다는 안내와 다시 불러오기 동작을 제공한다.
- 성공 후 상세 화면을 닫고 캘린더, 내역, 지갑 조회를 갱신한다.

### 데이터 계약 확인

- `query_transactions` 응답에 상세와 수정에 필요한 ID, version, memo, method/member 식별자가 없다면 새 migration에서 반환 필드를 추가한다.
- 다른 가계부 거래, 무효화 거래, 보관된 결제 수단을 이용한 임의 변경은 서버가 거절해야 한다.
- 상품권·환불 거래는 현재 수정 계약이 완성되지 않았으므로 일반 `income`/`expense`만 수정 대상으로 시작한다. 지원하지 않는 유형은 읽기 전용으로 표시한다.

### 완료 기준

- 일반 거래를 열어 수정하고 목록과 합계에서 변경값을 확인할 수 있다.
- 삭제 확인을 취소하면 아무 RPC도 호출하지 않는다.
- 삭제 성공 후 목록과 합계에서 거래가 제외된다.
- 오래된 version으로 수정하면 충돌 안내가 나오며 기존 서버 값을 덮어쓰지 않는다.
- 실패 시 사용자가 입력한 수정값이 유지된다.

### 테스트

- 상세 필드 렌더링과 수정 화면 초안 주입.
- 수정 성공/실패/버전 충돌.
- 삭제 확인 취소/성공/실패.
- repository 파라미터와 조회 갱신 횟수.
- pgTAP의 권한, version 증가, void 집계 제외 회귀.

## TX02 — 내역 기간·필터·페이지네이션

권장 브랜치: `feat/transaction-history-filters`

### 현재 문제

내역 탭은 선택 월 결과 중 첫 10건만 보여 주며 더 보기 안내가 없다. 기획에 있는 일/주/월 기간, 구성원·수단·카테고리 필터와 커서 페이지 이동 UI가 없다. repository도 사실상 첫 페이지에 머문다.

### 구현 범위

- 상단에 기간 단위 `일 / 주 / 월` 선택을 제공한다. 초기값은 월이다.
- 이전/다음 기간 이동과 현재 기간 제목을 제공한다.
- 구성원, 결제 수단, 카테고리 필터를 bottom sheet 또는 modal sheet로 제공한다.
- 적용된 필터는 칩으로 표시하고 개별 제거 및 전체 초기화를 지원한다.
- 목록과 합계는 반드시 동일한 기간·필터를 사용한다.
- `occurred_on`, `created_at`, `id` 커서로 다음 페이지를 불러온다. 새 페이지는 중복 없이 기존 목록 뒤에 추가한다.
- 필터나 기간이 변경되면 목록과 커서를 초기화하고 첫 페이지부터 조회한다.
- 100건 고정 잘림이나 `.take(10)`을 사용자에게 숨기지 않는다.

### 완료 기준

- 월 경계, 연도 경계, 월요일 시작 주간 이동이 정확하다.
- 필터 적용 후 합계와 목록이 같은 조건을 반영한다.
- 다음 페이지를 불러와도 중복이나 순서 뒤바뀜이 없다.
- 결과 없음, 마지막 페이지, 조회 실패와 재시도를 구분한다.
- 탭을 오갔다 돌아와도 현재 기간과 필터를 유지한다.

### 테스트

- 12월에서 다음 달 이동 시 1월 범위.
- 월 경계를 포함한 주간 범위.
- 필터 조합이 repository에 그대로 전달됨.
- 두 페이지 병합, 마지막 페이지, 페이지 재시도.
- 필터 변경 시 이전 결과와 커서 제거.

## TX03 — 거래 목록의 수입·지출 시각 구분

권장 브랜치: `feat/transaction-list-visual-semantics`

### 현재 문제

캘린더 선택 날짜와 내역 목록에서 금액이 모두 양수 형태로 보여 수입과 지출을 빠르게 구분하기 어렵다. 거래 종류도 행에 명시되지 않는다.

### 구현 범위

- 수입은 `+`, 지출은 `−` 부호를 사용한다.
- 색상만으로 의미를 전달하지 않고 부호와 현지화된 유형 텍스트 또는 아이콘을 함께 사용한다.
- 카테고리와 결제 수단 중 정보 우선순위를 정해 subtitle에 표시한다.
- 금액은 tabular figures를 유지하고 화면 전체에서 같은 형식을 사용한다.
- 접근성 라벨에 거래 유형, 사용처, 금액, 날짜를 포함한다.

### 완료 기준

- 흑백 또는 색각 차이가 있어도 수입과 지출을 구분할 수 있다.
- 캘린더와 내역의 동일 거래가 같은 금액 표현을 사용한다.
- 한국어·영어 및 큰 글자에서 행이 잘리지 않는다.

### 테스트

- 수입/지출 부호와 라벨.
- 큰 글자와 좁은 화면 레이아웃.
- 접근성 semantics 값.

## CAL01 — 캘린더 날짜별 수입·지출 표시

권장 브랜치: `feat/calendar-daily-summary`

### 현재 문제

캘린더는 날짜 선택기 역할만 한다. 어떤 날에 거래가 있는지, 수입·지출이 얼마인지 월 화면에서 파악할 수 없다. 기본 `CalendarDatePicker`는 날짜 셀에 사용자 정의 소계를 표시하기 어렵다.

### 구현 범위

- 먼저 현재 월 조회 결과를 날짜별 수입/지출 합계로 그룹화하는 순수 함수를 추가한다.
- 날짜 셀에는 최소한 거래 존재 점을 표시하고, 화면 폭이 허용되면 수입/지출 축약 금액을 표시한다.
- 오늘, 선택 날짜, 월 밖 날짜, 비활성 날짜의 시각 상태를 구분한다.
- 기존 `오늘` 버튼과 월 이동 동작을 유지한다.
- 기본 picker로 요구사항을 충족할 수 없다면 캘린더 패키지를 추가하기 전에 유지보수 상태, 라이선스, 접근성, 현지화 지원을 확인한다. 패키지 도입은 이 작업의 PR 설명에 근거를 남긴다.

### 제외 범위

- 거래 생성·수정 API 변경.
- 캘린더에서 드래그로 날짜 이동.

### 완료 기준

- 월의 각 날짜에서 거래 존재 여부를 확인할 수 있다.
- 날짜를 누르면 하단 목록이 그 날짜 거래로 바뀐다.
- 다른 월로 이동하고 오늘 버튼을 누르면 현재 월과 오늘 선택으로 돌아온다.
- 수입·지출 표시가 색상에만 의존하지 않는다.

### 테스트

- 날짜별 그룹 합계 순수 단위 테스트.
- 거래 있음/없음 날짜 렌더링.
- 월 이동, 날짜 선택, 오늘 복귀 회귀.

## DB01 — 저장 재시도 요청 ID 유지

권장 브랜치: `fix/transaction-save-idempotent-retry`

### 현재 문제

DB는 같은 `request_id`와 같은 본문을 재전송하면 기존 결과를 반환하지만, 앱의 직접 입력 재시도는 새 ID를 만들 수 있다. 서버가 저장했으나 응답만 유실된 경우 중복 거래가 생길 수 있다.

### 구현 범위

- 사용자가 저장을 처음 누를 때 요청 ID를 생성하고 저장 결과가 확정될 때까지 유지한다.
- 네트워크 오류 후 내용이 바뀌지 않은 재시도는 같은 요청 ID를 사용한다.
- 날짜, 금액, 사용처, 카테고리, 수단, 사용자, 메모 등 payload가 변경되면 새 요청 ID를 만든다.
- 성공하거나 입력을 폐기하면 요청 ID를 제거한다.
- `idempotency_conflict`는 일반 네트워크 오류와 구분해 안내한다.
- AI 일괄 저장의 기존 `saveRequestId` 동작과 규칙을 맞춘다.

### 완료 기준

- 같은 초안의 실패 후 재시도는 동일 요청 ID를 사용한다.
- 초안을 수정한 뒤 저장하면 새 요청 ID를 사용한다.
- 빠른 중복 탭은 RPC를 한 번만 호출한다.
- 응답 유실을 모의한 테스트에서 거래가 한 건만 생성되는 계약이 유지된다.

### 테스트

- repository fake로 요청 ID 캡처.
- 실패→무수정 재시도, 실패→수정→재시도, 성공 후 새 입력.
- 가능하면 pgTAP에서 같은 ID/같은 본문과 같은 ID/다른 본문 회귀.

## WAL01 — 상품권 생성·최초 충전 원자화

권장 브랜치: `feat/atomic-voucher-onboarding`

별도 DB·금융 계약 리뷰가 필요한 작업이다.

### 현재 문제

상품권 수단 생성과 최초 충전이 두 RPC로 실행된다. 두 번째 요청이 실패하면 빈 상품권만 남는다. 충전 시 출금 수단을 입력하거나 전달하지 않아 카드로 구매한 상품권 충전이 카드 실적에 귀속되지 않는다. 초기 보유 잔액과 유상 충전도 UI에서 구분되지 않는다.

### 구현 범위

- `초기 보유 잔액`과 `새로 구매한 충전`을 명시적으로 구분한다.
- 유상 충전은 실제 결제액, 충전액, 출금 수단, 실제 사용자를 받는다.
- 상품권 생성과 선택적인 최초 잔액/충전을 하나의 원자적 RPC로 처리한다.
- 초기 보유 잔액은 지출과 카드 실적을 만들지 않는다.
- 유상 충전은 실제 결제액만 지출에 포함하고, 출금 수단이 카드이면 해당 월 카드 실적에 포함한다.
- 동일 요청 재시도를 위한 request ID와 payload hash를 사용한다.
- 중간 실패 시 상품권 수단과 잔액 이동이 모두 롤백된다.

### 완료 기준

- 93,000원 결제, 100,000원 충전 시 지출 93,000원, 잔액 100,000원이다.
- 초기 잔액 100,000원은 지출 0원이다.
- RPC 실패 후 빈 상품권 수단이 남지 않는다.
- 카드 출금 수단을 선택하면 카드 예상 실적에 93,000원이 반영된다.
- 다른 가계부 수단이나 보관된 수단을 사용할 수 없다.

### 테스트

- 위 금액 예시, 초기 잔액, 원자적 롤백, 동일 요청 재시도.
- 다른 가계부/보관 수단/권한 없음.
- Flutter 폼 검증과 성공·실패 UI.

## INV01 — 전체 초대 링크 붙여넣기

권장 브랜치: `feat/invitation-link-paste`

### 현재 문제

딥링크로 앱이 열리면 토큰을 자동 입력하지만, 사용자가 카카오톡 메시지에서 전체 HTTPS 링크를 복사해 입력란에 붙여넣으면 48자리 토큰 검증에 실패한다. 입력란 `maxLength: 48` 때문에 URL 입력 자체도 불편하다.

### 구현 범위

- 초대 입력은 48자리 토큰과 허용된 호스트의 전체 HTTPS 링크, 개발용 `smartbudget://invite/<token>`을 받는다.
- 파싱은 `invitation_link.dart`의 한 함수에서 수행하고 온보딩과 설정 화면이 같은 함수를 사용한다.
- 허용되지 않은 scheme/host/path, 대문자 또는 잘못된 길이는 거절한다.
- 붙여넣은 링크에서 토큰을 추출한 뒤 입력란에는 토큰만 정규화해 보여도 된다.
- 허용 웹 호스트는 현재 앱 설정값을 사용하고 임의 호스트의 토큰을 수락하지 않는다.

### 완료 기준

- 토큰, 운영 HTTPS 링크, 개발용 커스텀 링크를 각각 수락한다.
- 악성 또는 유사 호스트 링크는 거절한다.
- 온보딩과 설정 화면의 동작이 같다.
- 토큰을 로그나 영구 저장소에 기록하지 않는다.

### 테스트

- 정상 토큰과 두 종류 링크.
- 잘못된 scheme, host, path, 길이, 문자를 가진 링크.
- 전체 링크 붙여넣기 후 repository에는 토큰만 전달됨.

- 모든 오류를 수정하면 저장 버튼이 활성화된다.
- 선택 해제한 항목의 오류는 전체 저장을 막지 않는다.

### 테스트

- 각 필수 필드 누락과 오류 문구.
- 선택 해제 시 저장 가능 여부 재계산.
- 필드 수정 후 오류 해제.
- 지원하지 않는 분석 유형 선택 차단.

## SYNC01 — 공동 데이터 수동 새로고침

- 새로고침은 현재 선택 월과 필터를 유지한다.
- 여러 future를 동시에 새로고침해야 하면 한 화면의 관련 데이터가 모두 완료될 때까지 진행 상태를 유지한다.
- 성공 토스트를 남발하지 않고 실패만 인라인으로 표시한다.

### 완료 기준

- 다른 세션에서 만든 데이터가 사용자의 새로고침 후 보인다.
- 새로고침 중 중복 요청이 무제한 발생하지 않는다.
- 실패 후 기존 데이터가 사라지지 않고 다시 시도할 수 있다.

### 테스트

- refresh gesture/action이 repository를 다시 호출함.
- 현재 월과 필터 유지.
- 실패 시 기존 데이터 유지.

## SYNC02 — 다른 구성원 변경 실시간 반영

권장 브랜치: `feat/household-realtime-sync`

### 선행 조건

SYNC01 완료 후 진행한다. 먼저 수동 새로고침으로 데이터 갱신 경계를 고정해야 한다.

### 구현 범위

- 활성 가계부의 거래, 결제 수단, 구성원 변경을 Supabase Realtime 또는 더 단순한 앱 재개 시 갱신으로 반영한다.
- 앱 생명주기, 로그인 사용자 변경, 가계부 탈퇴 시 기존 구독을 해제한다.
- 이벤트마다 개별 행을 복잡하게 병합하기보다 해당 화면의 repository 조회를 debounce하여 다시 실행하는 방식을 우선한다.
- RLS를 우회하는 공개 채널이나 service-role 키를 사용하지 않는다.

### 완료 기준

- 두 세션에서 한쪽이 거래를 저장하면 다른 쪽이 합리적인 시간 안에 갱신된다.
- 로그아웃 또는 탈퇴 후 이전 가계부 이벤트가 화면에 반영되지 않는다.
- 빠른 연속 이벤트가 과도한 전체 조회를 만들지 않는다.

### 테스트

- 가짜 이벤트 스트림으로 갱신/debounce/구독 해제.
- 사용자 및 가계부 변경 시 이전 스트림 무시.
- 실제 두 계정 검증은 별도 수동 결과로 기록.

## TIME01 — 업무 날짜 기준 통일

권장 브랜치: `fix/business-date-timezone`

### 결정 필요

현재 사용자가 한국 거주 부부라는 전제라면 업무 날짜를 `Asia/Seoul`로 고정하는 안이 단순하다. 해외 사용과 다국가 지원을 고려한다면 가계부별 시간대 필드가 필요하다. 구현 전에 둘 중 하나를 사용자에게 확인한다.

### 현재 문제

거래 기본 날짜, 오늘 버튼, 카드 실적 월, 상품권 이벤트 날짜가 각 위치의 `DateTime.now()`에 의존한다. 기기 시간대가 다르거나 자정 근처일 때 서로 다른 날짜를 사용할 수 있다.

### 구현 범위

- `오늘`과 업무 월을 계산하는 단일 주입 가능한 clock/date provider를 둔다.
- UI, repository 기본값, 테스트가 같은 기준을 사용한다.
- DB의 `date`와 기록 시각 `timestamptz`를 혼동하지 않는다.
- 기존 저장 데이터는 변경하지 않는다.

### 완료 기준

- 같은 순간에 캘린더 오늘, 새 거래 기본 날짜, 카드 실적 월이 일치한다.
- 자정 경계 테스트를 실제 시간 대기 없이 실행할 수 있다.
- 선택한 시간대 정책이 문서에 명시된다.

### 테스트

- 한국 자정 직전/직후 또는 선택한 가계부 시간대 경계.
- 12월 31일에서 1월 1일 전환.
- 주입한 고정 clock을 사용하는 위젯 테스트.

## ARCH01 — `main.dart` 화면 단위 분리

권장 브랜치: `refactor/split-main-screens`

### 목적

`main.dart`에 앱 시작, 인증 루트, 캘린더, 월 요약, 탭 상태, 설정 화면이 함께 있어 기능 변경 시 영향 범위가 크다. 이 작업은 사용자 기능을 추가하지 않는 구조 개선이다.

### 구현 범위

- 캘린더 관련 위젯을 `features/calendar/`로 이동한다.
- 월 요약과 거래 목록 표현은 사용하는 화면과 가까운 파일로 이동한다.
- 설정 화면을 `features/settings/`로 이동한다.
- `BudgetApp`은 탭 전환과 공통 의존성 전달에 집중한다.
- 공개 API와 현재 UI 동작을 유지한다.
- 상태 관리 패키지를 새로 도입하지 않는다.

### 제외 범위

- 디자인 변경, repository 재작성, 라우팅 패키지 도입, 전역 상태 관리 교체.

### 완료 기준

- 기존 사용자 동작과 렌더링이 유지된다.
- 기존 테스트를 대량 수정하지 않고 모두 통과한다.
- 이동한 위젯의 import 방향이 UI → repository 경계를 유지한다.

### 테스트

- 기존 전체 Flutter 테스트 무수정 통과를 우선한다.
- 파일 이동 때문에 필요한 최소 import 수정만 허용한다.
- `flutter analyze`, macOS debug build.

## 공통 수동 점검표

각 UI 작업은 자동 테스트 외에 아래 항목 중 관련된 것을 확인한다.

- iPhone SE 수준의 좁은 폭과 최신 Pro Max 수준의 큰 화면.
- 시스템 글자 크기 200%에서 잘림, overflow, 접근 불가능한 버튼이 없는지.
- 한국어와 영어 모두 확인.
- 밝은 테마 12개에서 텍스트 대비와 선택/오류/비활성 상태 확인.
- 로딩 중 뒤로 가기, 빠른 중복 탭, 네트워크 실패 후 재시도.
- 키보드가 열린 상태에서 마지막 필드와 주요 버튼에 접근 가능한지.
- VoiceOver/TalkBack을 위한 tooltip 또는 semantics가 있는지.
- 로그에 토큰, 이미지, 거래 내용, 내부 DB 오류가 노출되지 않는지.
